## 1순위 — 커밋 규칙

### 배경

이번 과제에서는 태스크 하나당 커밋 하나로 잘게 쪼개고, `feat:` `fix:` `docs:` 같은 접두사(Conventional Commits)를 붙였다.

그런데 회사에서는 반대 경험을 했다.

- 작업한 내용을 **통째로 하나로 커밋해서 달라**는 요청을 받은 적이 있다
- 회사 리포 커밋 이력에는 접두사가 **없는** 것 같다

### 질문

1. **우리 팀의 커밋 단위 기준은 어떻게 되나요?**
-   QA브랜치를 제외한 develop, main 등은 이슈 단위로 통으로 올린다.
-   QA브랜치는 테스트를 위한 브랜치이기 때문에 자유롭게 올리는 편이다.

2. 통째로 하나를 선호하셨던 건 어떤 이유였을까요?
- 이슈별 관리 및 rebase 등을 원할하게 하기 위해서이다.

3. 작업 중에는 잘게 쪼개두고 합칠 때 하나로 묶는 방식도 있다고 들었는데, 우리는 그렇게 하나요?
- 우리 회사의 경우 QA브랜치에서 자유롭게 커밋을 올리고, develop, main 브랜치에 옮길 때는 stash를 활용해서 정리하기도 한다.

4. 커밋 메시지에 접두사를 안 쓰는 특별한 이유가 있나요? 다른 회사들은 주로 쓰는 편인가요?
- 우리 회사는 정책이 없어서 그냥 적지만, 일반적으로 다른 회사들은 작성하는 편이다.

5. **제가 회사 작업을 커밋할 때는 어떤 형식으로 쓰는 게 좋을까요?**
- 정책은 따로 없지만 판매채널명, 이슈 번호는 들어가는 것이 좋다.
    - 예) [B2C] TTP-1545 복지몰 페이지 생성

### 내 가설

작업 중에는 되돌리기 쉽게 잘게 쪼개고, 본 브랜치에 합칠 때는 이력을 깔끔하게 하려고 하나로 묶는 — 두 요구가 공존하는 것 같다.

## 2순위 — API 데이터 다루기

프론트와 백엔드의 경계를 어디에 긋느냐의 문제라, 앞으로 계속 마주칠 판단이다.

### 배경

API 응답에서 쓸 필드를 추려 `docs/FIELDS.md`로 정리해봤다. 처음 해보는 작업이다.

그리고 작업 중에 **응답에 필요한 데이터가 없는** 상황을 만났다. 상품 카드에 할인가를 표시하려 했는데 dummyjson은 `price`와 `discountPercentage`만 주고 할인된 금액은 주지 않는다. 직접 계산해야 했고, 범위가 커져서 결국 M5로 미뤘다.

### 질문

1. **응답에 필요한 데이터가 없을 때는 어떻게 하나요?** 백엔드에 추가를 요청하는 게 맞나요, 프론트에서 계산하는 게 맞나요? 판단 기준이 있을까요?
- 응답에 필요한 데이터는 요청하는 게 맞지만, 프론트에서 처리를 하기 위한 로직인지는 백엔드 및 기획자와 확인 및 협의하여 판단. 보통은 백엔드에서 주지만 프론트에서 작업하는 경우도 있다.

    - 백엔드가 주는 게 맞는 경우
        * 계산 규칙이 복잡하거나 자주 바뀔 때 — 프론트가 5개 채널이면 규칙 바뀔 때마다 5군데를 고쳐야 한다.
        * 돈과 직결될 때 — 할인가, 적립금, 수수료. 프론트에서 계산하면 브라우저에서 조작할 수 있고, 실제 결제 금액과 어긋날 수 있다.
        * 여러 화면에서 같은 값이 필요할 때 — 목록·상세·장바구니에서 같은 할인가를 써야 하는데 각자 계산하면 어긋난다.

    - 프론트에서 하는 게 맞는 경우
        * 단순 표시 형식 — 2026-10-16 → 10월 16일
        * 화면에서만 쓰는 임시 계산 — 장바구니 합계
        * API를 고치는 비용이 더 클 때 (배포 일정, 다른 서비스 영향)

2. 실무에서 API를 받아 쓸 때 백엔드에서 **명세서를 따로 받나요?** 우리 회사는 어떤 형태로 공유되나요?
- 받는다.

3. 명세서가 있다면 제가 한 "쓸 필드 추리기"는 따로 필요한 작업인가요, 아니면 바로 코드로 들어가도 되나요?
- 일반적으로 기획자가 기획서를 주면 개발자가 미리 확인하여 필요한 필드를 생각한다. 그 후 회의를 통해 프론트, 백엔드, 기획자와 협의한다.


### 내 가설

명세서는 "이 API가 무엇을 주는가"이고, 내가 만든 문서는 "그중 이 화면이 무엇을 쓰는가"라서 층이 다른 것 같다. 혼자 하는 프로젝트라 필요했던 거고, 팀 작업에서는 과할 수도 있겠다 싶었다.

## 3순위 — 리소스 경로

당장 막힌 건 없지만 회사 소스를 읽다 생긴 의문이라 짚고 넘어가고 싶다.

### 배경

내 프로젝트에서 처음에 `<link href="/style.css">`로 썼다가 `./style.css`로 바꿨다. `/`로 시작하면 사이트 최상위부터 찾기 때문에, GitHub Pages처럼 하위 경로에 배포되면 깨진다고 해서다.

그런데 회사 소스에는 `/Travel/Domestic`, `/Promotion/List` 처럼 슬래시로 시작하는 경로가 많았다. 한편 `common.css` 안에서는 `url(../images/...)` 같은 상대경로를 쓰고 있었다.

### 질문

1. **라우트 경로와 정적 리소스 경로는 기준이 다른 건가요?**
* 일반적으로 상대경로로 작성하면 되고, github가 특이 케이스이다.
* 문제의 본질은 **”이 사이트가 도메인 루트에 배포되는가"**입니다.

| 배포 위치	| /style.css |
|---|---|
| triptopaz.com/ ← 루트	| ✅ 동작 |
| example.com/vanilla-shop/ ← 하위 경로	| ❌ 깨짐 |
||


### 내 가설

`/Travel/Domestic`은 서버가 해석하는 **URL**이고, `href="/style.css"`는 브라우저가 파일을 찾아가는 **경로**라 성격이 다른 것 같다. CSS 안의 `url(...)`은 CSS 파일 위치가 기준이라 상대경로를 쓰는 것으로 이해했다.
