# 브라우저 저장소 비교

장바구니를 새로고침 후에도 유지하기 위해 `localStorage` · `sessionStorage` · `document.cookie` 세 가지를 모두 구현하고 비교한 기록이다. (M3)

---

## 1. 비교 결과

| 실험 | localStorage | sessionStorage | cookie |
| ---- | ------------ | -------------- | ------ |
| 새로고침 후 유지 | ✅ | ✅ | ✅ |
| 새 탭에서 같은 사이트를 열면 | ✅ | ❌ | ✅ |
| 탭을 닫았다 다시 열면 | ✅ | ❌ | ✅ |
| 브라우저 완전 종료 후 재시작 | ✅ | ❌ | ✅ |
| **요청 헤더에 실려 가는가** | ❌ | ❌ | **✅** |
| 4KB를 넘는 데이터 | 문제없음 | 문제없음 | **저장되지 않음** |
| 저장·읽기 코드 | 간결 | 간결 | 문자열을 직접 파싱해야 함 |

| | 용량 한도 | 유효 범위 | 수명 |
| --- | --- | --- | --- |
| localStorage | 5~10MB | 오리진(사이트) | 명시적으로 지우기 전까지 |
| sessionStorage | 5~10MB | **탭** | 탭을 닫으면 소멸 |
| cookie | 약 4KB | 도메인 + 경로 | 설정한 만료 시점까지 |

---

## 2. 핵심 차이 — 서버로 가는가

세 저장소의 용량 한도가 1000배 이상 차이 나는 이유는 **쿠키만 네트워크 요청에 실려 나가기 때문**이다.

개발자도구 Network 탭에서 문서 요청의 Request Headers를 보면 쿠키 전체가 포함되어 있다. 같은 사이트의 `style.css`, `main.js` 요청에도 동일하게 붙는다. 반면 `localStorage`와 `sessionStorage`는 어떤 요청 헤더에도 나타나지 않는다.

```
새로고침 1회
├── index.html   → Cookie: cart=... (약 3KB)
├── style.css    → Cookie: cart=... (약 3KB)
├── main.js      → Cookie: cart=... (약 3KB)
└── favicon.ico  → Cookie: cart=... (약 3KB)
```

서버가 사용하지 않는 데이터도 매 요청마다 전송된다. 쿠키가 4KB로 제한된 것은 인색해서가 아니라, 크면 **모든 요청이 느려지기** 때문이다.

다른 도메인으로 가는 요청(`cdn.dummyjson.com` 이미지 등)에는 붙지 않는다. 쿠키는 도메인에 묶여 있다.

### 용도가 갈리는 지점

| | 적합한 데이터 |
| --- | --- |
| cookie | **서버가 알아야 하는** 작은 값 — 세션 ID, 언어 설정, A/B 테스트 그룹 |
| localStorage | 브라우저 안에서만 쓰는 데이터 — 사용자 설정, 임시 입력값 |
| sessionStorage | 탭 하나에서만 유효하면 되는 데이터 — 다단계 입력 폼의 중간 상태 |

### 보안

쿠키는 `HttpOnly` 옵션을 주면 JS가 읽을 수 없다. 세션 ID를 이 방식으로 보호한다. `localStorage`는 JS가 항상 읽을 수 있으므로 민감한 정보를 저장하지 않는다.

## 3. 탭 복제 — sessionStorage의 예외

`sessionStorage`는 탭 단위로 독립되어 있으나, **탭 복제(Duplicate tab)로 연 탭에는 내용이 복사된다.**

```
주소창에 입력해 새 탭 열기   →  새 세션 (빈 상태)
탭 복제                      →  기존 세션 복사 (내용 이어받음)
```

탭 복제는 주소만 복사하는 것이 아니라 세션 상태를 통째로 복사한다. 뒤로 가기 기록도 함께 따라온다.

---

## 4. 쿠키 구현에서 겪은 것

### 메서드가 없다

`localStorage`는 `setItem` · `getItem` 두 개로 끝나지만, 쿠키는 문자열을 직접 다룬다.

```js
// 저장 — 대입처럼 보이지만 덮어쓰기가 아니라 "하나 추가"다
document.cookie = `cart=${encodeURIComponent(JSON.stringify(cart))}; path=/; max-age=604800;`;

// 읽기 — 전체 쿠키가 한 문자열로 나오므로 직접 잘라내야 한다
const cookies = document.cookie.split("; ");
const cartCookie = cookies.find((item) => item.startsWith("cart="));
if (cartCookie) {
    return JSON.parse(decodeURIComponent(cartCookie.slice(5)));
}
return [];
```

### 인코딩이 필요하다

쿠키 문자열에서 `;` `,` `=` 공백은 구분자 역할을 한다. JSON에는 이런 문자가 포함되므로 `encodeURIComponent`로 감싸고 읽을 때 `decodeURIComponent`로 되돌린다.

### `slice(5)`를 쓴 이유

`split("=")`으로 자르면 값 안에 `=`가 들어 있을 때 조각이 셋 이상으로 나뉜다. `"cart="`가 다섯 글자이므로 `slice(5)`로 그 뒤를 전부 가져오는 편이 안전하다.

### 4KB를 넘기면 조용히 거부된다

상품 객체 전체를 담으면 1건에 약 3,000자, 2건이면 6,000자를 넘는다. 2건째 저장 시 **에러 없이 대입이 무시되어** 이전 값이 그대로 남았다. 화면에는 2로 표시되다가 새로고침하면 1로 돌아가는 증상으로 나타났다.

`localStorage`는 같은 데이터를 문제없이 저장했다.

## 5. 최종 선택 — localStorage

### 선택 이유

1. **장바구니 항목은 민감 정보가 아니다.** JS가 읽을 수 있는 저장소에 두어도 무방하다.
2. **상품 객체 전체를 담는 현재 설계와 맞는다.** 장바구니 상세 화면에서 이미지·브랜드·가격을 바로 쓰기 위해 객체 전체를 저장하기로 했고(M2-4), 그만한 용량이 필요하다.
3. **담아두기만 하는 사용자를 고려하면 용량 여유가 필요하다.** 위시리스트처럼 쓰는 경우 항목이 많아지는데, 쿠키 4KB로는 2건도 담지 못한다.

### 전제 조건

**로그인 기능이 없고 상품 데이터가 변하지 않는 현재 조건**에서의 결론이다.

- 로그인이 추가되면 서버 저장으로 옮긴다. `localStorage`는 그 브라우저에만 존재하므로 기기를 넘지 못한다. PC에서 담고 모바일에서 결제하는 흐름을 지원할 수 없다.
- 가격·재고처럼 변하는 값을 다루게 되면 저장 방식을 재검토한다. 저장된 값은 그 시점의 스냅샷이므로 시간이 지나면 실제와 달라진다.

### 참고 — 실무에서 흔한 방식

브라우저에 장바구니를 저장할 때는 보통 `id`와 수량만 담고 상품 정보는 매번 조회한다. 용량 때문이 아니라 **저장된 정보가 낡기 때문**이다.

회사 코드(hotel-web)의 찜 기능이 이 방식이다. Redis에는 호텔 번호 배열 `[7, 102, 3051]`만 저장하고, 화면을 그릴 때마다 번호로 상세 정보를 조회한다. 대신 호텔 1건당 외부 호출이 2회 발생해 20건이면 최대 40회가 된다.

| | 최신성 | 조회 비용 |
| --- | --- | --- |
| id만 저장 | 항상 최신 | 크다 |
| 객체 전체 저장 | 낡을 수 있음 | 없다 |

양쪽 모두 대가가 있다. 이 프로젝트는 데이터가 변하지 않으므로 후자를 택했다.
