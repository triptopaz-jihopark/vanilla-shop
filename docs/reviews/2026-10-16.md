## 1. 커밋 규칙

> 이번 과제에서는 태스크 하나당 커밋 하나로 잘게 쪼개고 `feat:` `fix:` `docs:` 접두사를 붙였다.
> 그런데 회사에서는 "작업한 내용을 통째로 하나로 커밋해서 달라"는 요청을 받은 적이 있고, 회사 리포 이력에는 접두사가 없다.

### Q1. 우리 팀의 커밋 단위 기준은 어떻게 되나요? ✅

- QA 브랜치를 제외한 develop, main 등은 **이슈 단위로 통으로** 올린다
- QA 브랜치는 테스트용이라 자유롭게 올린다

<details>
<summary>📖 브랜치마다 규칙이 다른 이유</summary>

| 브랜치 | 성격 | 커밋 |
|---|---|---|
| QA | 테스트용. 깨져도 되는 곳 | 자유롭게, 잘게 |
| develop / main | 팀이 공유하는 본줄기 | 이슈 하나 = 커밋 하나 |

QA 브랜치는 **작업장**이고 develop/main은 **진열장**이다. 작업장에서는 톱밥이 날려도 되지만 진열장에는 완성품만 올린다.

학습 리포는 전부 작업장에 해당하므로 지금처럼 잘게 쪼개는 방식도 틀리지 않다. 회사 develop에 올릴 때만 규칙이 달라진다.

</details>

### Q2. 통째로 하나를 선호하는 이유는? ✅

이슈별 관리 및 **rebase**를 원활하게 하기 위해서.

<details>
<summary>📖 rebase와 커밋 개수의 관계</summary>

**rebase**는 내 작업을 최신 기준점 위로 옮겨 붙이는 것이다.

작업하는 동안 develop에 다른 사람 코드가 쌓이면, 내 작업은 옛 시점에서 갈라져 나왔으므로 그대로 합치면 이력이 꼬인다. rebase는 내 커밋을 떼어 최신 develop 끝에 다시 붙인다.

> 책에 메모지를 붙여뒀는데 그사이 개정판이 나온 상황. 메모지를 떼어 새 책의 해당 페이지에 다시 붙이는 것.

여기서 커밋 개수가 결정적이다.

- 커밋 1개 → 충돌이 나도 **한 번만** 해결
- 커밋 15개 → 커밋마다 충돌 검사. 최악의 경우 **15번** 해결

중간 커밋은 대부분 "작업 중" 상태라 그 시점으로 돌아가 충돌을 풀어도 의미가 없다. 그래서 합칠 때는 하나로 묶는 편이 압도적으로 편하다.

</details>

### Q3. 작업 중엔 쪼개고 합칠 때 묶는 방식인가요? 🔄

우리 회사는 QA 브랜치에서 자유롭게 커밋하고, develop·main으로 옮길 때 **stash를 활용해서 정리**하기도 한다.

<details>
<summary>📖 stash와 squash는 다른 도구 — 후속 확인 필요</summary>

| | 무엇을 다루나 | 하는 일 |
|---|---|---|
| **stash** (스태시) | 아직 **커밋 안 한** 변경분 | 서랍에 잠시 넣어두고 꺼내기 |
| **squash** (스쿼시) | 이미 **커밋된** 여러 개 | 눌러서 하나로 합치기 |

squash는 "짓누르다", stash는 "숨겨두다"라는 뜻이다.

**stash로는 이미 쌓인 커밋을 합칠 수 없다.** 그래서 멘토 답변은 두 가지로 해석된다.

**해석 A — 실제 stash 워크플로**
```
QA에서 커밋 없이 작업 → stash → develop 이동 → stash pop → 커밋 1개
```
커밋을 애초에 안 만들었으니 합칠 것이 없다.

**해석 B — squash를 말한 것**
```
QA에서 커밋 10개 → develop에 합칠 때 squash → 커밋 1개
```

답변이 "QA에서 자유롭게 커밋을 올리고"로 시작하므로 B에 가까워 보인다. 다음 회차에서 실제 명령어를 확인할 것. (→ 후속 ①)

</details>

### Q4. 접두사를 안 쓰는 이유가 있나요? ✅

우리 회사는 **정책이 없어서** 그냥 적지 않는다. 일반적으로 다른 회사들은 작성하는 편이다.

### Q5. 회사 작업 커밋은 어떤 형식으로 쓰면 좋을까요? ✅

정책은 없지만 **판매채널명과 이슈 번호**는 들어가는 것이 좋다.

```
[B2C] TTP-1545 복지몰 페이지 생성
```

<details>
<summary>📖 각 부분이 하는 일</summary>

| 부분 | 역할 |
|---|---|
| `[B2C]` | 어느 **판매채널** 작업인지. 채널이 5개라 없으면 매번 열어봐야 한다 |
| `TTP-1545` | **이슈 번호**. 이슈 추적 도구의 티켓과 연결 |
| `복지몰 페이지 생성` | 무엇을 했는지 |

이슈 번호가 있으면 커밋과 이슈가 양방향으로 연결된다. 커밋을 보고 "이게 왜 필요했지?" → 이슈에서 요구사항 확인. 반대로 이슈에서 "어떻게 고쳤지?" → 커밋 찾기.

이 형식은 접두사(`feat:`)와 충돌하지 않는다. 회사에서는 회사 형식, 학습 리포에서는 접두사를 써도 된다. 팀 관례에 맞추는 쪽이 우선이다.

**웹매거진 작업 시 이슈 번호가 있는지 확인할 것.**

</details>

## 2. API 데이터 다루기

> 응답에 필요한 데이터가 없는 상황을 만났다. 상품 카드에 할인가를 표시하려 했는데 dummyjson은 `price`와 `discountPercentage`만 주고 할인된 금액은 주지 않는다. 결국 M5로 미뤘다.

### Q1. 응답에 필요한 데이터가 없을 때는 어떻게 하나요? ✅

요청하는 것이 맞지만, 프론트에서 처리할 로직인지는 **백엔드 및 기획자와 협의하여 판단**한다. 보통은 백엔드에서 주지만 프론트에서 작업하는 경우도 있다.

<details>
<summary>📖 실무에서 갈리는 기준</summary>

**백엔드가 주는 편이 맞는 경우**

- 계산 규칙이 **복잡하거나 자주 바뀔 때** — 프론트가 5개 채널이면 규칙이 바뀔 때마다 5군데를 고쳐야 한다
- **돈과 직결될 때** — 할인가, 적립금, 수수료. 프론트 계산은 브라우저에서 조작할 수 있고 실제 결제 금액과 어긋날 수 있다
- **여러 화면에서 같은 값**이 필요할 때 — 목록·상세·장바구니가 각자 계산하면 값이 어긋난다

**프론트에서 하는 편이 맞는 경우**

- 단순 표시 형식 — `2026-10-16` → `10월 16일`
- 화면에서만 쓰는 임시 계산 — 장바구니 합계
- API 수정 비용이 더 클 때 (배포 일정, 다른 서비스 영향)

할인가는 돈이고 여러 화면에서 쓰이므로 **백엔드 쪽에 가깝다.** dummyjson이 주지 않는 것은 연습용 더미 API이기 때문이다.

</details>

## 3. 리소스 경로

> `<link href="/style.css">`를 `./style.css`로 바꿨다. `/`로 시작하면 사이트 최상위부터 찾기 때문에 하위 경로 배포 시 깨진다.
> 그런데 회사 소스에는 `/Travel/Domestic` 처럼 슬래시로 시작하는 경로가 많았고, `common.css` 안에서는 `url(../images/...)` 상대경로를 쓰고 있었다.

### Q. 라우트 경로와 정적 리소스 경로는 기준이 다른가요? ✅

일반적으로 **상대경로로 작성**하면 되고, GitHub가 특이 케이스다.

<details>
<summary>📖 문제의 본질은 "도메인 루트에 배포되는가"</summary>

| 배포 위치 | `/style.css` |
|---|---|
| `triptopaz.com/` ← 루트 | ✅ 동작 |
| `example.com/vanilla-shop/` ← 하위 경로 | ❌ 깨짐 |

GitHub Pages가 하위 경로로 배포되는 대표 사례라 언급된 것이다. 같은 일이 생기는 경우가 또 있다.

- 사내 포털 아래에 붙는 서비스 (`portal.company.com/hr/`)
- 리버스 프록시로 여러 앱을 한 도메인에 모을 때
- 로컬에서 상위 폴더를 열어 띄웠을 때

**상대경로는 어디에 배포되든 동작한다.** 그래서 기본값으로 안전하다.

**라우트와 리소스가 다른 이유** — 누가 해석하느냐의 차이.

```
<a href="/Travel/Domestic">   → 서버가 받아서 어느 컨트롤러로 보낼지 판단
<link href="/style.css">       → 브라우저가 직접 파일을 찾으러 감
```

라우트는 **서버에게 보내는 주소**라 반드시 루트 기준이어야 한다. 라우팅 규칙이 `/Travel/Domestic` 형태로 등록돼 있으므로, 상대경로로 쓰면 현재 페이지 위치에 따라 엉뚱한 곳을 가리킨다.

반면 CSS·JS·이미지는 **파일을 찾아가는 길**이라 상대경로가 성립한다. CSS 안의 `url(...)`은 CSS 파일 위치가 기준이다.

> 라우트는 "서울시 강남구 테헤란로"처럼 절대 주소여야 하고, 리소스는 "여기서 두 블록 앞"처럼 상대 안내가 가능하다.

</details>

## 4. 멘토 추가 피드백

- 스크립트 태그의 `defer`, `async`에 대해서 공부하기
  - 일반적으로 스크립트 태그는 닫는 `body` 위에 작성하나, `defer`를 사용하면 `head`에 작성할 수 있다
- `async`/`await`를 **동기/비동기에 중점**을 두고 공부하기
- 자바스크립트 **이벤트 루프**에 대해 공부하기
- **코드를 타이핑하는 것보다 코드를 보고 분석할 수 있는 능력**을 키워야 한다. 코드를 많이 보는 것이 도움이 된다
- 연습용 객체부터 화면에 뿌려보고 M1-4로 넘어갈 것

<details>
<summary>📖 앞의 세 가지는 하나로 이어지는 줄기</summary>

```
defer / async  →  동기 / 비동기  →  이벤트 루프
   (현상)          (개념)           (원리)
```

같은 주제를 세 층위에서 보는 것이므로 위에서부터 내려간다. 이벤트 루프는 M3에서 비동기 때문에 실제로 헷갈리는 상황을 겪은 뒤에 다룬다.

</details>

<details>
<summary>📖 defer / async / 옵션 없음 — 세 가지 비교</summary>

차이는 **언제 HTML 파싱을 멈추느냐**이다.

**옵션 없음** — 다운로드하는 동안에도 멈춰 있다.
```
파싱 ━━━━[정지ーーーーーーーーーー]━━━━ 파싱
         └ 다운로드 ━━━━ 실행 ┘
```

**async** — 다운로드는 파싱과 동시에, 실행할 때만 멈춘다.
```
파싱 ━━━━━━━━━━━━[정지]━━━━ 파싱
   └ 다운로드 ━━━━━┘ 실행
```

**defer** — 다운로드는 동시에, 실행은 파싱이 끝난 뒤.
```
파싱 ━━━━━━━━━━━━━━━━━ 완료 ─ 실행
   └ 다운로드 ━━━━━━┘ (대기)
```

| | 다운로드 중 파싱 | 실행 중 파싱 | 실행 시점 | 순서 보장 |
|---|---|---|---|---|
| 옵션 없음 | ❌ 멈춤 | ❌ 멈춤 | 태그 위치에서 | ✅ |
| `async` | ✅ 계속 | ❌ 멈춤 | 다운로드 끝나는 즉시 | ❌ |
| `defer` | ✅ 계속 | — | 파싱 완료 후 | ✅ |

**async가 아끼는 것은 "다운로드를 기다리는 시간"이다.** 파일이 크거나 네트워크가 느릴수록 차이가 커진다. 실행하는 시간만큼은 똑같이 멈춘다.

**HTML이 다 로드되기 전에 실행될 수 있는가** — `async`도 옵션 없는 것도 둘 다 그렇다. `head`에 옵션 없이 두면 HTML을 다 읽기 전에 실행된다. 그래서 전통적으로 `</body>` 위에 둔 것이다. **`defer`만 파싱 완료를 보장한다.**

**어느 쪽을 쓰나** — 파일 출처(내 프로젝트냐 외부냐)가 아니라 **의존성**이 기준이다.

| 질문 | 그렇다면 |
|---|---|
| 다른 스크립트를 필요로 하는가? | `defer` |
| HTML 요소를 건드리는가? | `defer` |
| 혼자 독립적으로 도는가? | `async` 가능 |

CDN에서 불러오는 jQuery는 남의 파일이지만 `defer` 쪽이다. 다른 스크립트가 `$`를 쓰려면 먼저 실행돼야 하므로.

</details>

### 확인한 것 — `_Layout.cshtml`

구글 애널리틱스 스크립트에만 `async`가 붙어 있고, 나머지 js 파일에는 옵션이 없다.

<details>
<summary>📖 둘 다 이유가 있다</summary>

**GA에 `async`** — 교과서적으로 맞다. 분석 스크립트는 다른 코드와 상관없고, 언제 실행되든 되고, 순서도 무관하다. `async`의 정석 용례.

**나머지에 옵션 없음** — 확인이 하나 더 필요하다. **그 스크립트들이 `head`에 있는가, `</body>` 직전에 있는가?**

- `</body>` 직전이면 → 옵션이 필요 없다. 어차피 HTML을 다 읽은 뒤라 `defer`를 붙여도 얻는 것이 거의 없다. 합리적인 선택
- `head`에 있으면 → 파싱이 멈춰 첫 화면이 늦게 뜬다. 개선 여지가 있다

그리고 **순서 문제**가 있다. B2C는 jQuery 기반이다.

```
jquery-3.4.1.min.js   ← 먼저
ui.js                 ← $ 사용
Common.js             ← $ 사용
```

순서가 깨지면 `$ is not defined` 에러가 난다. `async`는 순서를 보장하지 않으므로 쓰면 안 된다. 옵션 없이 두면 적어도 순서는 확실하다.

사실 **`defer`를 붙여도 순서는 보장되면서 다운로드는 병렬**이라 더 빠르다. 안 붙어 있다는 것은 코드가 `defer`가 널리 쓰이기 전에 작성됐거나 건드릴 이유가 없었다는 뜻으로 보인다. (→ 후속 ②)

</details>
