## 지난 회차 후속

### ① stash인가 squash인가 ✅

지난 회차에서 "QA 브랜치에서 자유롭게 커밋하고, develop·main으로 옮길 때 stash를 활용해서 정리한다"고 들었다. 그런데 찾아보니 stash와 squash는 다른 도구이고, **stash로는 이미 쌓인 커밋을 합칠 수 없는** 것으로 보인다.

|            | 무엇을 다루나              | 하는 일                     |
| ---------- | -------------------------- | --------------------------- |
| **stash**  | 아직 **커밋 안 한** 변경분 | 서랍에 잠시 넣어두고 꺼내기 |
| **squash** | 이미 **커밋된** 여러 개    | 눌러서 하나로 합치기        |

> **"QA에서 올린 커밋을 develop으로 옮길 때, 실제로 치는 명령어가 어떻게 되나요?"**

**답변**: squash가 맞고, 합쳐서 올릴 떄 강제 푸시를 써야하기 떄문에 내 로컬에 있는 커밋만 합칠 때 사용하는 것이 좋다.

### ② 스크립트에 `defer`를 안 붙인 이유 ✅

`_Layout.cshtml`을 확인한 결과, 구글 애널리틱스에만 `async`가 붙어 있고 나머지 외부 스크립트 13개는 `head`에 옵션 없이 있었다.

순서 의존성(jQuery → 플러그인 → 자사 js)이 있으니 `async`는 쓸 수 없다. 다만 `defer`는 순서를 지키면서 다운로드는 병렬로 하므로 쓸 수 있을 것 같은데 붙어 있지 않다.

인라인 스크립트가 중간중간 섞여 있어서, 외부 스크립트에만 `defer`를 붙이면 인라인이 먼저 실행되어 순서가 뒤집히는 것이 이유일까 싶다.

> **"외부 스크립트에 `defer`를 붙이면 첫 화면이 빨라질 것 같은데, 인라인 스크립트와 섞여 있어서 순서가 뒤집힐 것 같더라고요. 그래서 안 붙인 건가요, 아니면 다른 이유가 있을까요?"**

**답변**: 프론트가 조각조각 나뉘어 있는 경우가 많고, 그 조각 안에서 스크립트를 불러오는 경우도 있어서 그런 것 같다.

<details>
<summary>📖 조각(Partial / ViewComponent)과 defer가 충돌하는 이유</summary>

### Razor 화면은 조각들의 합이다

브라우저가 받는 HTML 한 장은 여러 파일이 합쳐진 결과다.

```
_Layout.cshtml          ← 뼈대
 ├ Top/Default.cshtml   ← 헤더 조각 (ViewComponent)
 ├ Home/Index.cshtml    ← 본문
 ├ _MainSearch.cshtml   ← 검색 조각
 └ _Maintenance.cshtml  ← 점검 안내 조각
```

**각 조각이 자기 스크립트를 직접 들고 있을 수 있고**, 그 스크립트는 조각이 그려지는 위치 — 즉 `body` 한가운데 — 에 인라인으로 박힌다.

### 실제 증거

`Views/Shared/Components/Top/Default.cshtml` 끝부분에 이 코드가 있다.

```html
<script>
    $(document).ready(function () {
        $("#topLogo").click(function () {
            localStorage.clear();
        });
    });
</script>
```

`$`를 쓰고 있다. jQuery가 **이미 실행돼 있어야** 동작한다.

### defer를 붙이면 깨진다

```
현재 (옵션 없음)                    defer 적용 시
─────────────────                  ─────────────────
head : jQuery 실행 ✓               head : (실행 예약만)
body : $(document).ready ✓         body : $(document).ready ✗  ← $ 없음!
                                   head : jQuery 실행 (이미 늦음)
```

`defer`는 **파싱이 끝난 뒤** 실행인데, 조각의 인라인 스크립트는 **파싱 도중** 실행된다. 순서가 뒤집혀 `$ is not defined` 에러가 난다.

### 왜 어려운 문제인가

`_Layout` 한 파일만 보고 판단할 수 없다. **수십 개 조각을 전부 열어 인라인 스크립트가 있는지 전수조사**해야 하고, 하나라도 놓치면 그 페이지만 조용히 깨진다.

`_Layout`에서 한 줄 고치는 일이 프로젝트 전체 점검이 되는 셈이다. 안 건드린 이유로 충분하다.

### 이것이 번들러가 필요한 이유

문제의 뿌리는 "화면 조각이 자기 스크립트를 직접 들고 있다"는 구조에 있다.

React 같은 방식에서는 컴포넌트가 `<script>` 태그를 들고 다니지 않는다. 모든 JS가 **빌드 도구를 거쳐 하나로 묶인 뒤** 한 번에 로드되므로 로딩 순서 문제가 애초에 생기지 않는다. M6에서 도입할 Vite가 그 "묶어주는 도구"다.
