## 2. vanilla-shop — 구조 정리 (멘토 피드백 ② 반영)

> 2026-11-05 피드백 — "현재 작성한 스크립트는 기능이 나열된 형태인데, 최상위가 컨트롤하는 형식으로 작성해보기."

2026-10-22 회차에서 미뤄두었던 질문("한 파일 안에서의 정리 기준")에 대한 답에 해당한다.

### 기존 구조의 문제

변수 → 함수 → 실행 → 변수 → 실행 → 함수 순으로 섞여 있었다. 실행되는 코드가 94행과 106행에 흩어져 있어, 파일을 처음 보는 사람은 **어디서 시작되는지 파악하기 위해 전체를 훑어야** 했다.

### 적용한 구조

```
1. 요소    DOM 참조
2. 상태    데이터
3. 함수    정의만, 실행 없음
4. 시작    init() 정의 및 호출
```

```js
function init() {
    cart = loadCart();       // 저장된 장바구니 복원
    updateCartCount();       // 헤더 반영

    productList.addEventListener("click", handleProductListClick);
    render();                // 상품 목록 그리기
}

init();
```

**파일에서 스스로 실행되는 코드는 `init()` 한 줄**이다. 나머지는 모두 선언이다.

### 진행 단계

동작을 바꾸지 않는 작업이므로 단계마다 화면을 확인하고 커밋했다.

| 커밋 | 내용 |
| ---- | ---- |
| `1707cb6` | 사용하지 않는 코드 제거 |
| `cddccd9` | 흩어진 요소·상태 선언을 상단으로 이동 |
| `268496a` | 익명 이벤트 핸들러를 이름 있는 함수로 분리 |
| `eeed364` | `init` 생성 후 실행 코드 이동 |
| `73eb248` | `init` 내부 순서 조정 |

세 번째 단계가 네 번째를 가능하게 한다. 핸들러에 이름이 있어야 `init`에서 연결할 수 있기 때문이다. 125줄에서 91줄로 줄었다.

### 판단한 부분 — `init` 내부 순서

처음에는 `render()`를 먼저 호출하고 장바구니 복원을 뒤에 두었다. 동작에는 문제가 없었으나 **코드를 읽는 순서와 실제 실행 순서가 달랐다.** `render()`는 비동기 함수이므로 `await`를 만나면 반환되고, 그동안 아래 코드가 먼저 실행된다.

복원을 앞으로 옮겨 "상태를 먼저 복원한 뒤 화면을 그린다"는 순서로 맞췄다.

리스너를 `render()`보다 먼저 등록한 것은 **이벤트 위임을 사용했기 때문에 가능하다.** 버튼마다 등록하는 방식이었다면 대상이 존재해야 하므로 `render()` 이후여야 한다.

## 3. vanilla-shop — M3 저장소 비교 (M3 완료)

`localStorage` · `sessionStorage` · `document.cookie` 세 가지를 모두 구현하고 비교했다. 정리 문서는 **`docs/STORAGE.md`**에 있다.

### 교체가 두 줄로 끝난 이유

저장·복원을 함수로 분리해두었다(M3-5).

```js
function saveCart() {
    localStorage.setItem("cart", JSON.stringify(cart));
}

function loadCart() {
    return JSON.parse(localStorage.getItem("cart")) ?? [];
}
```

저장 방식이 바뀌어도 **이 두 함수 안만 고치면 되고 호출하는 쪽은 바뀌지 않는다.** 회사 코드의 `IRedisFavoriteRepository`와 같은 구조다.

### 비교 결과

| 실험 | localStorage | sessionStorage | cookie |
| ---- | ------------ | -------------- | ------ |
| 새로고침 후 유지 | ✅ | ✅ | ✅ |
| 새 탭에서 같은 사이트 | ✅ | ❌ | ✅ |
| 탭을 닫았다 다시 열면 | ✅ | ❌ | ✅ |
| 브라우저 재시작 | ✅ | ❌ | ✅ |
| **요청 헤더에 실려 가는가** | ❌ | ❌ | **✅** |
| 4KB 초과 | 문제없음 | 문제없음 | **저장되지 않음** |
| 코드 간결성 | 간결 | 간결 | 직접 파싱 필요 |

### 핵심 — 쿠키만 서버로 간다

Network 탭에서 문서 요청의 Request Headers를 확인하니 장바구니 전체가 포함되어 있었다. 같은 사이트의 `style.css`, `main.js` 요청에도 동일하게 붙었고, 다른 도메인(`cdn.dummyjson.com`)에는 붙지 않았다.

```
새로고침 1회
├── index.html   → Cookie: cart=... (약 3KB)
├── style.css    → Cookie: cart=... (약 3KB)
└── main.js      → Cookie: cart=... (약 3KB)
```

**쿠키가 4KB로 제한된 것은 매 요청마다 네트워크로 전송되기 때문**이다. 서버가 쓰지 않는 데이터도 함께 간다. `localStorage`는 브라우저 밖으로 나가지 않으므로 5~10MB를 허용한다.

### 겪은 것 — 4KB 초과는 조용히 거부된다

상품 2건을 담자 화면에는 2로 표시되다가 새로고침하면 1로 돌아갔다. 상품 객체 전체를 담으면 1건에 약 3,000자이고 2건이면 6,000자를 넘는다. **`document.cookie` 대입이 에러 없이 무시되어** 이전 값이 그대로 남은 것이다.

M2-4 노트에 "M3에서 저장소에 담을 때 다시 검토한다"고 적어둔 지점이 이것이었다.

### 최종 선택 — localStorage

1. 장바구니 항목은 민감 정보가 아니므로 JS가 읽을 수 있는 저장소에 두어도 무방하다.
2. 상품 객체 전체를 담는 현재 설계(M2-4)와 맞는다. 장바구니 상세에서 이미지·브랜드·가격을 바로 쓰기 위해서다.
3. 위시리스트처럼 담아두기만 하는 사용자를 고려하면 용량 여유가 필요하다. 쿠키 4KB로는 2건도 담지 못한다.

**전제 조건을 명시했다.** 로그인 기능이 없고 상품 데이터가 변하지 않는 현재 조건에서의 결론이다. 로그인이 추가되면 서버 저장으로 옮겨야 하고(기기를 넘지 못하므로), 가격처럼 변하는 값을 다루게 되면 `id`만 저장하는 방식을 재검토한다.

## 4. 이번 구간에서 반복된 패턴

M3에서 만난 문제는 모두 **에러 없이 틀리는** 종류였다.

| 증상 | 원인 |
| ---- | ---- |
| `[object Object]`가 저장됨 | `setItem`이 값을 문자열로 변환 |
| `JSON.parse(null)`이 `null` 반환 | `String(null)`이 `"null"`이고 유효한 JSON |
| 쿠키에 코드 문자열이 그대로 저장 | 백틱이 아니어서 `${}`가 치환되지 않음 |
| 2건째부터 저장 안 됨 | 4KB 초과, 대입이 무시됨 |

증상이 나타나는 지점과 원인이 떨어져 있어, **중간값을 직접 확인하는 과정**이 필요했다. 개발자도구 Application 탭과 Network 탭이 그 역할을 했다.
